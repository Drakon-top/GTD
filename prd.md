## 1. Обзор приложения и цели

### 1.1 Описание
Персональное GTD-приложение (Getting Things Done), реализующее классическую методологию Дэвида Аллена с возможностью расширения пользовательскими категориями. Приложение предоставляет изолированные контексты (до 5) для разных сфер жизни, каждый со своим визуальным оформлением. Поддерживает работу в офлайн-режиме на Android с последующей синхронизацией.

### 1.2 Цели проекта
- Создать надёжную персональную GTD-систему, которой можно доверять на 100%
- Обеспечить работу в офлайн-режиме — задачи можно создавать и редактировать без интернета
- Предоставить чистый минималистичный интерфейс в стиле Notion/Obsidian
- Прокачать навыки Java backend-разработки (REST API, очереди сообщений, деплой)

### 1.3 Ключевые принципы
- **Фокус** — изолированные контексты, никакого смешения сфер
- **Доверие системе** — уведомления и напоминания работают безотказно
- **Простота** — минималистичный UI, быстрое добавление задач
- **Офлайн-first** — мобильное приложение полноценно работает без интернета

### 1.4 Тип продукта
Personal tool — однопользовательское приложение с авторизацией.

## 3. Основные функции и функциональность

### 3.1 GTD-система (ядро)

#### 3.1.1 Стандартные GTD-списки
Каждый контекст содержит следующие предустановленные списки:

| Список | Описание | Поведение |
|--------|----------|-----------|
| **Inbox** | Входящие задачи, мысли, идеи | Точка входа для всех новых задач |
| **Next Actions** | Конкретные следующие шаги | Задачи, которые можно выполнить прямо сейчас |
| **Projects** | Задачи, требующие >1 шага | Контейнер для подзадач с прогресс-баром |
| **Waiting For** | Делегированные/ожидающие задачи | С указанием кого/чего ждём |
| **Someday/Maybe** | Идеи на будущее | Низкий приоритет, без дедлайнов |
| **Reference** | Справочные материалы | Хранилище информации без действий |
| **Calendar** | Привязанные к дате задачи | С конкретной датой/временем |
| **Выполнено** | Завершённые задачи | Архив выполненных задач |

**Acceptance Criteria:**
- Пользователь видит все GTD-списки в боковом меню при входе в контекст
- Задачи можно перемещать между списками drag-and-drop или через меню
- Каждый список показывает счётчик задач
- Список "Выполнено" доступен, но визуально отделён от активных списков

#### 3.1.2 Кастомные категории
Пользователь может создавать собственные категории внутри контекста.

**Примеры:** Книги для чтения, Фильмы, Отзывы о книгах, Рецепты

**Модель категории:**
| Поле | Тип | Обязательное | Описание |
|------|-----|-------------|----------|
| id | UUID | Да | Уникальный идентификатор |
| context_id | UUID (FK) | Да | Привязка к контексту |
| name | String (100) | Да | Название категории |
| icon | String (50) | Нет | Иконка (emoji или icon name) |
| color | String (7) | Нет | Цвет в HEX формате |
| sort_order | Integer | Да | Порядок отображения |
| task_count | Integer | Да | Счётчик задач (computed) |
| is_deleted | Boolean | Да | Soft delete флаг |
| created_at | Timestamp | Да | Дата создания |
| updated_at | Timestamp | Да | Дата последнего обновления |

**Acceptance Criteria:**
- Пользователь может создать кастомную категорию с названием, иконкой и цветом
- Категории отображаются в боковом меню ниже стандартных GTD-списков
- Можно менять порядок категорий
- Задачам можно присвоить категорию при создании или позже
- Отображается счётчик задач в каждой категории
- Категории удаляются через soft delete

#### 3.1.3 Задачи (Tasks)

**Модель задачи:**
| Поле | Тип | Обязательное | Описание |
|------|-----|-------------|----------|
| id | UUID | Да | Уникальный идентификатор |
| context_id | UUID (FK) | Да | Привязка к контексту |
| parent_task_id | UUID (FK) | Нет | Родительская задача (для подзадач) |
| gtd_list | Enum | Да | GTD-список (INBOX, NEXT_ACTIONS, PROJECTS, WAITING_FOR, SOMEDAY_MAYBE, REFERENCE, CALENDAR, DONE) |
| category_id | UUID (FK) | Нет | Пользовательская категория |
| title | String (500) | Да | Название задачи |
| notes | Text | Нет | Заметки к задаче (plain text) |
| due_date | Timestamp | Нет | Дедлайн |
| reminder_settings | JSON | Нет | Настройки напоминаний |
| recurrence_rule | JSON | Нет | Правило повторения |
| nesting_level | Integer (1-4) | Да | Уровень вложенности (1 = корневая) |
| sort_order | Integer | Да | Порядок внутри списка |
| is_completed | Boolean | Да | Статус выполнения |
| completed_at | Timestamp | Нет | Дата выполнения |
| is_deleted | Boolean | Да | Soft delete флаг |
| created_at | Timestamp | Да | Дата создания |
| updated_at | Timestamp | Да | Дата последнего обновления |
| version | Integer | Да | Версия для синхронизации |

**Acceptance Criteria:**
- Пользователь может создать задачу с минимумом — только название
- Задачу можно обогатить: заметки, дедлайн, категория, напоминания
- Задачи можно перемещать между GTD-списками
- Выполненные задачи перемещаются в список "Выполнено"
- Удалённые задачи помечаются is_deleted=true, не удаляются из БД

#### 3.1.4 Вложенные подзадачи

**Максимальная вложенность: 4 уровня**

Задача (уровень 1)
└── Подзадача (уровень 2)
└── Подзадача (уровень 3)
└── Подзадача (уровень 4) — максимум

sql

**Acceptance Criteria:**
- Подзадачи создаются внутри родительской задачи
- Максимум 4 уровня вложенности, при попытке создать 5-й — показать ошибку
- Подзадачи наследуют контекст родительской задачи
- Прогресс родительской задачи вычисляется по количеству выполненных подзадач
- При выполнении родительской задачи — предложить выполнить все подзадачи
- При soft delete родительской задачи — подзадачи также помечаются как удалённые

#### 3.1.5 Повторяющиеся задачи

**Поддерживаемые паттерны:**
| Паттерн | Пример | recurrence_rule JSON |
|---------|--------|---------------------|
| Ежедневно | Каждый день в 9:00 | `{"type": "daily", "time": "09:00"}` |
| Еженедельно | Каждый понедельник | `{"type": "weekly", "day_of_week": 1, "time": "09:00"}` |
| Кастомный интервал | Каждые 3 дня | `{"type": "custom", "interval_days": 3, "time": "09:00"}` |

**Acceptance Criteria:**
- При выполнении повторяющейся задачи автоматически создаётся следующий экземпляр
- Новый экземпляр наследует все свойства оригинала (контекст, категория, напоминания)
- Выполненный экземпляр перемещается в "Выполнено" с отметкой о повторении
- Пользователь может остановить повторение в любой момент

- Каждый контекст полностью изолирован: свои задачи, категории, GTD-списки
- Пользователь может менять тему контекста в настройках контекста
- Попытка создать 6-й контекст показывает ошибку с сообщением о лимите
- Контексты удаляются через soft delete

### 3.3 Уведомления

#### 3.3.1 Типы уведомлений (фиксированный набор для MVP)

| Тип | Триггер | Пример |
|-----|---------|--------|
| **Напоминание по времени** | Наступило время напоминания | "Через 15 минут: встреча с командой" |
| **Дедлайн** | За 24 часа до дедлайна | "Завтра дедлайн: сдать отчёт" |
| **Повторяющаяся задача** | Время выполнения повторяющейся задачи | "Ежедневно: проверить Inbox" |
| **Конфликт синхронизации** | Обнаружен конфликт при sync | "Задача X была изменена на другом устройстве" |

#### 3.3.2 Кастомные напоминания

**Модель напоминания:**
| Поле | Тип | Обязательное | Описание |
|------|-----|-------------|----------|
| id | UUID | Да | Уникальный идентификатор |
| task_id | UUID (FK) | Да | Привязка к задаче |
| remind_at | Timestamp | Да | Точное время напоминания |
| offset_type | Enum | Нет | Тип смещения (MINUTES, HOURS, DAYS, WEEKS) |
| offset_value | Integer | Нет | Значение смещения |
| is_sent | Boolean | Да | Было ли отправлено |
| created_at | Timestamp | Да | Дата создания |

**Пример:** Задача "День рождения друга" с дедлайном 15 марта:
- Напоминание 1: за 1 неделю (8 марта)
- Напоминание 2: за 1 день (14 марта)
- Напоминание 3: в день события (15 марта, 9:00)

**Acceptance Criteria:**
- К одной задаче можно привязать несколько напоминаний
- Напоминания доставляются как Android Push-уведомления
- Уведомления работают даже если приложение закрыто
- В офлайн-режиме напоминания работают на основе локальных данных
- При нажатии на уведомление — открывается задача в приложении

### 3.4 Прогресс и статистика

#### 3.4.1 Прогресс-бар проектов

**Формула:** `прогресс = (выполненные подзадачи / общее количество подзадач) × 100%`

Учитываются все уровни вложенности.

**Визуализация:** Горизонтальный прогресс-бар рядом с названием проекта.

📁 Редизайн сайта [████████░░░░] 65% (13/20)
📁 Переезд [██░░░░░░░░░░] 15% (3/20)

shell

#### 3.4.2 Счётчики задач

Каждый GTD-список и категория отображает количество активных задач.

📥 Inbox (5)
⚡ Next Actions (12)
📁 Projects (4)
⏳ Waiting For (3)
💭 Someday/Maybe (8)
📎 Reference (15)
📅 Calendar (6)
✅ Выполнено (142)
─────────────────────
📚 Книги (7)
🎬 Фильмы (3)

bash

**Acceptance Criteria:**
- Прогресс-бар отображается для каждого проекта в списке Projects
- Прогресс обновляется в реальном времени при выполнении подзадач
- Счётчики задач видны в боковом меню рядом с названием списка/категории
- Счётчики не учитывают задачи с is_deleted=true

7. Соображения по безопасности
7.1 Аутентификация
Email + пароль с хэшированием через BCrypt

Весь трафик через HTTPS (TLS 1.3)
Rate limiting: максимум 100 запросов в минуту на пользователя
Валидация всех входных данных на backend
Защита от SQL Injection через параметризованные запросы (JPA)
CORS настройка — только разрешённые домены
7.3 Данные
Пароль никогда не хранится в открытом виде
Локальные данные на Android не шифруются (решение для MVP)
JWT токены на Android хранятся в EncryptedSharedPreferences

8.2 Алгоритм синхронизации (Smart Merge)
Шаг 1: При каждом изменении на Android — запись в локальную таблицу pending_changes:

bash
{entity: "task", id: "xxx", field: "title", new_value: "...", timestamp: "..."}
Шаг 2: При появлении интернета WorkManager запускает sync:

Отправить все pending_changes на сервер
Получить изменения с сервера с момента последней синхронизации
Применить серверные изменения к локальной БД
Шаг 3: Разрешение конфликтов (field-level merge):

text
Для каждого изменённого поля:
  ЕСЛИ поле изменено ТОЛЬКО на клиенте → применить клиентскую версию
  ЕСЛИ поле изменено ТОЛЬКО на сервере → применить серверную версию
  ЕСЛИ поле изменено на ОБОИХ:
    → Применить версию с более поздним timestamp
    → Создать уведомление о конфликте
    → Записать в Sync_Log с conflict_status = RESOLVED_NOTIFY
Шаг 4: Уведомить пользователя о конфликтах (если были).

8.3 Acceptance Criteria — Синхронизация
Все операции CRUD работают офлайн на Android
Синхронизация запускается автоматически при появлении интернета
Field-level merge корректно объединяет неконфликтующие изменения
Пользователь получает push-уведомление при конфликтах
Данные не теряются при конфликтах (обе версии записываются в Sync_Log)
Web-приложение всегда работает только онлайн (нет офлайн-режима)

Spring @Scheduled задачи:

Каждый час: проверить приближающиеся дедлайны → добавить в очередь
Ежедневно в 00:00: создать экземпляры повторяющихся задач на сегодня
Technical Considerations — Очередь:
Использовать dead letter queue для неудавшихся уведомлений
Реализовать retry с exponential backoff (3 попытки)
Логировать все отправленные и неудавшиеся уведомления

12. Потенциальные проблемы и способы их решения
Проблема	Риск	Решение
Сложность синхронизации	Высокий	Начать с простого last-write-wins, итеративно усложнять до field-level merge. Покрыть тестами все edge cases
Офлайн-уведомления	Средний	AlarmManager для локальных уведомлений, тестировать в airplane mode
Производительность Room при большом количестве задач	Низкий	Пагинация, индексы на часто фильтруемые поля (context_id, gtd_list, is_deleted)
Консистентность UI между Web и Android	Средний	Определить единый design system (цвета, отступы, шрифты) до начала разработки UI
Повторяющиеся задачи — edge cases	Средний	Что если задача не выполнена, а уже время новой? Решение: создавать новый экземпляр всегда, старый помечать как просроченный
JWT-токены и офлайн	Средний	Хранить refresh token с долгим сроком жизни (30 дней), обновлять access token при появлении сети
FCM в России	Средний	Протестировать доставку push через FCM. Если есть проблемы — рассмотреть Yandex Push SDK как альтернативу
Масштаб Phase 1-7	Высокий	Строго следовать этапам, не перепрыгивать. Каждый phase — рабочий инкремент
